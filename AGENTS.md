## Commands

- `npm run dev` (Turbopack dev server), `npm run build`, `npm run lint`.
- No tests, no CI, no pre-commit hooks in this repo. Verify changes with `npm run lint` (bare `eslint`, whole repo) and `npm run build`.

## Toolchain quirks

- Tailwind v4 with **no `tailwind.config`**: theme/design tokens live in `src/app/globals.css`. Tailwind is wired through a Turbopack rule (`@tailwindcss/turbopack`) in `next.config.ts` — don't remove that rule or CSS imports break.
- **React Compiler is enabled** (`reactCompiler: true` in `next.config.ts`). Write hooks/components according to the Rules of React; don't add `useMemo`/`useCallback`/`React.memo` for optimization.

## shadcn/ui

- Style is `base-nova` (see `components.json`): UI primitives come from **`@base-ui/react`, not Radix** — don't import Radix in new components.
- `src/components/ui/` already contains the full installed component set (many not yet used by app code).
- To add more: `npx shadcn@latest add <component>`; aliases are `@/components`, `@/lib`, `@/hooks`, `@/lib/utils` (`cn` re-exported from the `cn` package in `src/lib/utils.ts`).
- Code highlighting uses Shiki with the JS regex engine and per-language lazy imports — register new languages in `src/lib/highlighter.tsx`.

## Structure

- App code lives in `src/app` (App Router). Right now it contains only the scaffold home page (`page.tsx`) and `layout.tsx`; `src/components/ui`, `src/hooks`, `src/lib` are library code.
- `better-auth` is wired up server-side in `src/lib/auth.ts` (email+password + google provider) with `@better-auth/mongo-adapter` to the Atlas cluster in `.env` `BETTER_AUTH_DB_URI` (connection verified working; PING OK). `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are NOT set in `.env` yet, so Google sign-in cannot work until they are. User records carry an additional `role` field ("seeker" | "recruiter" | "admin", default "seeker") that the client can set at sign-up — `user.additionalFields.role` with `input: true` (security caveat documented in `auth.ts`: any visitor can register as admin; tighten before production). Client lives in `src/lib/auth-client.ts` — a single `authClient` instance (handlers re-exported from it, don't create a second client).
- Auth pages (`(auth)` route group) render `AuthCard` (`src/components/auth/auth-card.tsx`, client): one component handles both modes ("sign-in"/"sign-up") with a segmented toggle navigating between routes. Form submit is wired to better-auth (`authClient.signIn.email` / `signUp.email`); a page can override it with AuthCard's optional `onSubmit(data)` prop (as `sign-up/page.tsx` does). Contract: on success AuthCard itself waits 1.5s and `router.push("/")`; a page handler signals failure by **throwing** (real better-auth message shows in the red banner) or returning `false`. The Google button is still a placeholder (`handleGoogle` only logs) — token is only visible in the response object it logs or the httpOnly `better-auth.session_token` cookie, never "in console" on its own.
- Job dialogs (`src/components/jobs/`): `DeleteJobDialog` (trash-icon trigger, destructive confirm dialog "Yes, delete job", calls `deleteJob` DELETE `/jobs/:id` from `lib/api/jobs.ts`, then `router.refresh()`; client component) and `ViewJobDialog` (eye-icon trigger, read-only details from the row object, no extra fetch), plus shared `types.ts` exporting `JobPostRow` (JobInput + optional `_id`, applicants, status, postedAt). Row actions order: View → Update (Link to `/dashboard/recruiter/jobs/new?edit=<id>` — form does NOT pre-fill yet) → Delete; the ⋮ button was removed. Client dialogs required because the page itself is a server component.
- Manage Jobs page (`/dashboard/recruiter/jobs`, per the user's Figma screenshot): single-file dark page — breadcrumb "Manage Jobs › Job Listings & Postings", "Manage Job Posts" heading, violet "+ New Job Post" pill button (top-right, links to jobs/new), and an 8-column table (Job Title & Dept, Company & Location, Type, Compensation, Applicants, Status, Deadline, Actions) in `overflow-x-auto` wrapper with `min-w-[960px]` (responsive = scroll on mobile). Row type `JobPostRow = JobInput & { id, applicants: string (FormData only yields strings), status: "Active"|"Expired", postedAt }` — base fields mirror the New Job form; `DUMMY_JOB_POSTS` array supplies 5 rows (Active/Expired badges with dot, category→icon map, currency symbol map, fixed-locale deadline formatting). Update/trash/⋮ action buttons are no-op placeholders. everything lives in `page.tsx` itself (client component, no separate form component — the earlier `src/components/jobs/new-job-form.tsx` was deleted at the user's request). Dark page (`dark` wrapper, `#0b0b0f`, section panels `#131317`, inputs `#1a1a20`): breadcrumb "Manage Jobs › Create New Listing", heading "Post a New Job", sections "1. Basic Information" (title, company name w/ icon, category select, 4 job-type chips), "2. Location, Compensation & Timeline" (isRemote toggle card w/ switch disabling location, location + deadline icon inputs, min/max salary, frequency select), "3. Responsibilities & Requirements" (two textareas), Publish Job button at the **bottom** (not top-right). Data collection: one `FormData`/`Object.fromEntries` → console.log (TODO: POST /api/jobs). The Figma `.fig`'s embedded images were all decorative/logos — screen details come from the requirements doc; dashboard main area is light-themed (default), only the sidebar is dark.
- `auth-client.ts` uses the `inferAdditionalFields<typeof serverAuth>()` plugin (type-only server import) so `session.user.role` is typed "seeker" | "recruiter" | "admin" everywhere.
- Dashboard sidebar: `src/app/components/DashboardSidebar.tsx` — `MenuItem { id, name, url, icon: LucideIcon }`, `menuItemsByRole: Record<UserRole, MenuItem[]>` fills menus from `Project requirements.md` pages (`/dashboard/<role>/...`; recruiter menu per Figma screenshot: Dashboard, Manage Jobs, Applications, Settings — no "My Company"/"Add Job" entries). Per user decision: no role group label ("admin menu" removed) and no public-links "Explore" section — sidebar shows only the role menu. Renders: Logo header, role menu, footer with user info (initials avatar, name, email · role) and Logout (`signOut()` → `router.push("/")` + `refresh()`). `role` is `undefined` while `isPending`. Which menu renders comes from `session.user.role` in MongoDB — recruiter edits won't appear while logged in with an admin-role account (e.g. `admin@admin.com`).
- The home page is dark themed and **the navbar is page-mounted**, not in the root layout: `page.tsx` renders `<SiteNavbar />` inside `<main className="dark">` so the area behind the bar is dark (no white strip). Other pages must mount it themselves inside their theme wrapper if they want it.
- The navbar is deliberately near-full-bleed (side margins `px-4 sm:px-6 xl:px-10`, ~94% viewport width per the Figma mock) — it does NOT use the shared Container. `Container` (`max-w-7xl px-4 sm:px-6`, from `src/components/layout/container.tsx`) is for centered content sections like the hero; full-bleed visuals (hero globe, capped at `max-w-[90rem]` centered) sit outside it.
- Design source: screenshot-driven, colors from the navbar/hero mocks (`#1b1b1f` surface, `brand` violet tokens in `globals.css`). Brand assets: `public/images/logo.png` is the real wordmark, wrapped by `Logo` in `src/components/layout/logo.tsx` (re-exported from `site-navbar.tsx`); `globe.png`/`cta-bg.png` are hero/CTA art with transparent middles. Project requirements + Framer Motion conventions live in `c:\Projects\Hireloop resources\hireloop-resources\` (outside the repo).
- Auth pages (`(auth)` route group) render `AuthCard` (`src/components/auth/auth-card.tsx`, client): one component handles both modes ("sign-in"/"sign-up") with a segmented toggle that navigates between the two routes. Form submit only collects `FormData` and logs it — better-auth integration is intentionally not wired yet (there's a TODO at the handler).
